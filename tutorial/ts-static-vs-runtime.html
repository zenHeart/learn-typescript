# TypeScript 静态类型与运行时行为差异

本节深入探讨 TypeScript 编译期类型检查与运行时实际行为之间的根本差异，帮助开发者避免「编译通过 = 运行时安全」的误区。

# 1. 类型擦除（Type Erasure）

# 核心概念

TypeScript 编译器的首要目标是类型安全，但这些类型信息仅存在于编译阶段。一旦编译完成，类型信息会被完全擦除，生成的 JavaScript 代码中不包含任何类型注解。

TypeScript (有类型)  ──编译──>  JavaScript (无类型)
     ↓
  类型检查
     ↓
  类型擦除

# 类型擦除的本质

// 类型擦除示例
// TypeScript 类型在编译后被完全移除

function identity<T>(arg: T): T {
  return arg;
}

interface Point {
  x: number;
  y: number;
}

const p: Point = { x: 1, y: 2 };

// 泛型参数 T 在运行时不存在
function checkType<T>(value: T) {
  // typeof T 永远不会是 'string' 或其他具体类型
  // 因为 T 在运行时被擦除了
  console.log(typeof T); // 永远输出: undefined
  return value;
}

// 尝试在运行时检查泛型类型是不可能的
const str = checkType("hello");
const num = checkType(42);

// 类型擦除后的编译结果
// 所有类型注解被移除

function identity(arg) {
  return arg;
}

const p = { x: 1, y: 2 };

function checkType(value) {
  // T 被完全擦除！
  console.log(typeof T); // 报错: T is not defined
  return value;
}

const str = checkType("hello");
const num = checkType(42);

观察编译后的 JavaScript 代码，我们发现：

  1. 所有类型注解（: string, : number, : boolean）全部消失
  2. 泛型 <T> 被完全移除
  3. 接口、类型别名在运行时不存在

# 运行时不存在 typeof T

// typeof T 在泛型函数中的行为

function logger<T>(value: T) {
  console.log('typeof T:', typeof T);      // 永远输出: undefined
  console.log('typeof value:', typeof value); // 真实类型

  // 错误示例：尝试用 typeof T 做类型判断
  if (typeof T === 'string') {  // 永远为 false！
    // 这段代码永远不会执行
    return value.toUpperCase();
  }

  return value;
}

logger("hello");   // typeof T: undefined, typeof value: string
logger(42);        // typeof T: undefined, typeof value: number
logger(true);      // typeof T: undefined, typeof value: boolean

// typeof-generic.ts 的运行时演示
// 在浏览器控制台运行以下代码

function logger(value) {
  console.log('typeof value:', typeof value);

  // 正确的做法：用 typeof value 而不是 typeof T
  if (typeof value === 'string') {
    console.log('Value is string:', value.toUpperCase());
  }

  return value;
}

logger("hello");
logger(42);
logger(true);

关键点：typeof T 在泛型函数内部永远返回 "undefined"（或具体原始类型），因为泛型参数 T 在运行时已经被擦除。

WARNING

不要在运行时尝试检查泛型类型！泛型是纯编译期概念，运行时没有任何信息。

# 2. 编译选项与运行时保障

# strictNullChecks

// strictNullChecks 编译期 vs 运行期
// 编译选项只影响编译，运行时无任何保障

// strictNullChecks: true 时，编译会报错
let name: string = 'Alice';
// name = null;    // Error: Type 'null' is not assignable to type 'string'
// name = undefined; // Error: Type 'undefined' is not assignable to type 'string'

// 即使编译通过，运行时仍然可能出错
let name2: string = 'Bob';
name2 = null as any; // 绕过类型检查

// 运行时会崩溃！
// console.log(name2.toUpperCase()); // TypeError: Cannot read properties of null

// 正确做法：显式处理 null/undefined
let name3: string | null = 'Charlie';
if (name3 !== null) {
  console.log(name3.toUpperCase()); // 安全
}

// strict-null-checks.ts 编译后的 JavaScript
// 没有任何类型保护

let name = 'Alice';
name = null;    // 赋值成功，没有任何检查
name = undefined; // 赋值成功，没有任何检查

// 运行时会崩溃
try {
  console.log(name.toUpperCase());
} catch (e) {
  console.error('Error:', e.message); // Cannot read properties of null
}

// 正确做法：运行时手动检查
let name3 = 'Charlie';
if (name3 !== null) {
  console.log(name3.toUpperCase()); // CHARLIE
}

核心差异：

  • 编译期：strictNullChecks 让你声明 name: string 时不能赋值为 null
  • 运行期：null 和 undefined 是真实存在的值，没有任何类型保护
编译选项 编译期行为 运行期保障
strictNullChecks: true 报错 null 不能赋给 string 无任何保障
strictNullChecks: false 不报错 无任何保障

# noImplicitAny

// noImplicitAny 演示
// noImplicitAny: true 时，隐式 any 会报错

// noImplicitAny: false (默认)
function process(data) {  // data 隐式为 any
  return data.value;      // 不报错，但危险！
}

// noImplicitAny: true
function processSafe(data: any) {  // 显式声明为 any
  return data.value;
}

// 即使编译通过，运行时也可能出错
const result = process(null); // 返回 undefined，不会报错
console.log(result); // undefined

// implicit-any.ts 编译后的 JavaScript
// any 类型在运行时没有任何保护

function process(data) {
  return data.value;
}

function processSafe(data) {
  return data.value;
}

const result = process(null); // 返回 undefined，不报错
console.log(result); // undefined

// 运行时行为完全一样，没有任何类型保护

# useDefineForClassFields

此选项影响 class field 的 emit 方式：

// class fields 编译选项影响
// useDefineForClassFields 选项影响 class field 的 emit 方式

class Base {
  x = 1;
}

class Derived extends Base {
  x = 2;
  y = 3;
}

// 当 useDefineForClassFields: true 时
// 编译为使用 Object.defineProperty

// 当 useDefineForClassFields: false 时
// 编译为简单的属性赋值

// class-fields.ts 编译后的 JavaScript
// useDefineForClassFields: true 时

var Base = /** @class */ (function () {
  function Base() {
    Object.defineProperty(this, "x", {
      enumerable: true,
      configurable: true,
      writable: true,
      value: 1
    });
  }
  return Base;
}());

var Derived = /** @class */ (function () {
  function Derived() {
    // super() 会调用 Object.defineProperty 设置 x
    // 然后子类设置 x = 2
    this.x = 2;
    this.y = 3;
  }
  return Derived;
}());
选项值 编译行为 运行时行为
true 使用 Object.defineProperty 符合 class 语义
false 直接赋值 可能与预期不符

# 3. Class Field 的 TS vs JS 行为差异

# declare 字段

class User {
  declare name: string;
  age: number;

  constructor(age: number) {
    this.age = age;
  }
}

const user = new User(18);
console.log(user.name); // undefined

class User {
  constructor(age) {
    this.age = age;
  }
}

const user = new User(18);
console.log(user.name); // undefined

关键点：

  • declare 字段仅用于类型检查，编译后完全消失
  • 运行时会报错 Cannot read property，因为属性不存在

# 抽象类字段

abstract class Shape {
  abstract area(): number;

  describe(): string {
    return `面积: ${this.area()}`;
  }
}

class Circle extends Shape {
  constructor(private radius: number) { super(); }
  area(): number { return Math.PI * this.radius ** 2; }
}

console.log(new Circle(2).describe());

class Shape {
  describe() { return `面积: ${this.area()}`; }
}

class Circle extends Shape {
  constructor(radius) { super(); this.radius = radius; }
  area() { return Math.PI * this.radius ** 2; }
}

console.log(new Circle(2).describe());
console.log(new Shape().describe()); // TypeError

抽象字段：

  • 编译期：检查子类是否实现了抽象属性
  • 运行期：抽象类不能实例化，抽象字段只是类型约束

# 访问器（Accessor）的特殊性

class User {
  private _name = '';

  get name(): string {
    return this._name;
  }

  set name(value: string) {
    this._name = value.trim();
  }
}

const user = new User();
user.name = '  Ada  ';
console.log(user.name); // Ada

TypeScript 的 accessor 关键字会生成 __accessor 相关代码，而不仅仅是简单的属性赋值。

# 4. Enum 在运行时的真实形态

# Numeric Enum 编译结果

enum Status {
  Pending,
  Running,
  Done,
}

console.log(Status.Pending); // 0
console.log(Status[0]);      // Pending

var Status;
(function (Status) {
  Status[Status["Pending"] = 0] = "Pending";
  Status[Status["Running"] = 1] = "Running";
  Status[Status["Done"] = 2] = "Done";
})(Status || (Status = {}));

console.log(Status.Pending); // 0
console.log(Status[0]);      // Pending

关键点：

  1. Numeric enum 编译为双向映射对象
  2. 可以通过值找到名字（反向映射）
  3. 运行时是普通 JavaScript 对象

# String Enum 编译结果

enum Direction {
  Up = 'UP',
  Down = 'DOWN',
}

console.log(Direction.Up); // UP

var Direction;
(function (Direction) {
  Direction["Up"] = "UP";
  Direction["Down"] = "DOWN";
})(Direction || (Direction = {}));

console.log(Direction.Up); // UP

差异：

  • String enum 没有反向映射
  • 编译产物更简单

# 运行时可修改性

enum Status {
  Pending,
  Done,
}

// 运行时对象可被改写；TypeScript 不会阻止
(Status as unknown as Record<string, unknown>).Pending = 99;
console.log(Status.Pending); // 99

var Status;
(function (Status) {
  Status[Status["Pending"] = 0] = "Pending";
  Status[Status["Done"] = 1] = "Done";
})(Status || (Status = {}));

Status.Pending = 99;
console.log(Status.Pending); // 99

DANGER

Enum 在运行时应被视为常量，但技术上可以被修改！修改后会影响所有引用。

# Const Enum 的特殊性

const enum Status {
  Pending,
  Done,
}

const current: Status = Status.Done;
console.log(current); // 1

// const enum 在编译后消失，使用处直接内联为数字
var current = 1;
console.log(current); // 1

关键点：

  • Const enum 在编译时内联化，完全不生成运行时对象
  • 但使用 --preserveConstEnums 可以保留编译产物

# 5. 类型断言（as）的危险性

# 核心问题

// 类型断言的危险性
// as 只在编译期有效，运行时没有任何类型保障

// 危险示例1：null 被断言为 string
const danger1 = null as string;
console.log("danger1:", danger1.toUpperCase()); // 💥 运行时报错

// 危险示例2：undefined 被断言为具体类型
const danger2 = undefined as { name: string };
console.log("danger2:", danger2.name.toUpperCase()); // 💥 运行时报错

// 危险示例3：API 返回的任意数据被断言为具体类型
interface User {
  id: number;
  name: string;
  email: string;
}

// 模拟 API 返回错误数据
const apiResponse = { error: "Not authorized", code: 401 };
const user = apiResponse as User;
console.log("user:", user.name.toUpperCase()); // 💥 运行时报错

// 正确做法：使用类型守卫
function safeGreet(name: string | null | undefined) {
  if (typeof name === "string") {
    return "Hello, " + name.toUpperCase();
  }
  return "Hello, stranger";
}

console.log(safeGreet("Alice")); // ✅ "Hello, ALICE"
console.log(safeGreet(null)); // ✅ "Hello, stranger"
console.log(safeGreet(undefined)); // ✅ "Hello, stranger"

// TypeScript 的 as 不会产生任何运行时检查
const data = JSON.parse('{"name": 42}');

// 断言成 { name: string } 后，运行时依旧是数字
const user = data;
console.log(typeof user.name); // number

as 只在编译期有效，运行时没有任何类型保障！

# 常见危险场景

interface User {
  name: string;
}

const raw: unknown = JSON.parse('{"name": 42}');

// 危险：as 不校验运行时结构
const user = raw as User;
console.log(user.name.toUpperCase()); // 运行时 TypeError

运行时会直接崩溃，因为 null.toUpperCase() 不存在。

# 正确的做法：类型守卫

// 类型守卫 - 在编译期和运行期都有效

// 场景：处理多种可能类型的参数
function processValue(value: string | number | boolean | null | undefined) {
  // typeof 是真正的运行时检查
  if (typeof value === "string") {
    // TypeScript 在这个分支中知道 value 是 string
    console.log("String length:", value.length);
    return value.toUpperCase();
  }
  
  if (typeof value === "number") {
    // TypeScript 在这个分支中知道 value 是 number
    console.log("Number to fixed:", value.toFixed(2));
    return value * 2;
  }
  
  if (typeof value === "boolean") {
    // TypeScript 在这个分支中知道 value 是 boolean
    return !value;
  }
  
  // 这里是 null | undefined
  return "No value provided";
}

// 测试
console.log(processValue("hello")); // String length: 5, HELLO
console.log(processValue(123.456)); // Number to fixed: 123.46, 246.912
console.log(processValue(true)); // false
console.log(processValue(null)); // No value provided
console.log(processValue(undefined)); // No value provided

function isUser(value) {
  return value !== null && typeof value === 'object' && typeof value.name === 'string';
}

const raw = JSON.parse('{"name": 42}');
console.log(isUser(raw)); // false

运行时不崩溃，因为 typeof value === 'string' 在运行时是真实的检查。

# 6. Declaration Files (d.ts)

# declare 语句的本质

// 只声明类型，不生成任何运行时代码
declare const VERSION: string;

console.log(VERSION); // 运行时由宿主环境提供

// declare 不会生成 JavaScript；VERSION 必须由宿主注入
console.log(typeof VERSION); // 取决于宿主环境

关键点：

  • declare 语句只生成类型，不生成任何 JavaScript 代码
  • 编译后 declare 语句完全消失

# declare global

export {};

declare global {
  interface Window {
    __APP_VERSION__: string;
  }
}

console.log(window.__APP_VERSION__);

// declare global 只影响类型检查，不会创建 window.__APP_VERSION__
console.log(typeof window.__APP_VERSION__); // undefined（若宿主未注入）

WARNING

declare global 只影响全局类型作用域，不会在运行时创建任何全局变量！

# 三斜线指令

/// <reference types="node" />

// 三斜线指令只影响编译期类型加载，不生成运行时代码
const version: string = process.version;
console.log(version);

// 三斜线指令不会出现在编译产物里
console.log(typeof process.version); // string

三斜线指令在 .ts 文件中是引用声明文件，但在 .js 文件中会被当作普通注释处理。

# 7. 条件类型（Conditional Types）

# 编译期求值

type IsString<T> = T extends string ? true : false;

type A = IsString<'hello'>; // true
type B = IsString<42>;      // false

// 条件类型只存在于编译期，运行时没有 IsString
console.log(typeof IsString); // undefined

关键点：

  • 条件类型在编译期求值折叠
  • 运行时不存在条件类型，只有具体的结果类型

# 分布式条件类型

type ToArray<T> = T extends unknown ? T[] : never;

type Result = ToArray<string | number>;
// string[] | number[]

// 分布式条件类型在编译期展开，运行时无对应结构
const values = ['a', 1];
console.log(values.map((v) => [v]));

# never 类型在条件类型中

type FilterString<T> = T extends string ? T : never;

type Result = FilterString<string | number | boolean>;
// string

// never 只影响类型层，不会删除运行时的值
const values = ['a', 1, true];
console.log(values.filter((v) => typeof v === 'string'));

# 8. 常见误区和坑

# 误区一：认为编译通过 = 运行时正确

interface User {
  name: string;
}

function printName(user: User) {
  console.log(user.name);
}

// 编译通过，但运行时会拿到不符合接口的数据
printName(JSON.parse('{"name": null}') as User);

function printName(user) {
  console.log(user.name);
}

printName(JSON.parse('{"name": null}')); // null

编译通过，但运行时报错！

# 误区二：用 as 假装有类型安全

type Admin = { role: 'admin' };

const guest = { role: 'guest' };
const admin = guest as unknown as Admin;

console.log(admin.role); // guest：as 没有改变运行时

const guest = { role: 'guest' };
const admin = guest;

console.log(admin.role); // guest

# 误区三：忽略 undefined/null 的运行时存在

interface Config {
  timeout?: number;
}

const config: Config = {};
console.log(config.timeout + 1); // NaN，TypeScript 不报错

const config = {};
console.log(config.timeout + 1); // NaN

# 误区四：认为接口会在运行时存在

interface User {
  name: string;
}

// interface 不会生成运行时校验
const user = {} as User;
console.log(user.name); // undefined

const user = {};
console.log(user.name); // undefined

# 9. 运行时类型验证方案

# Zod 的使用

import { z } from 'zod';

const User = z.object({ name: z.string() });
const parsed = User.parse(JSON.parse('{"name":"Ada"}'));

console.log(parsed.name); // Ada

// 运行时校验由 zod 完成；无效输入会抛错
// const User = z.object({ name: z.string() });
// User.parse(JSON.parse('{"name":42}')); // ZodError
console.log('zod 在运行时校验结构');

# io-ts 的使用

import * as t from 'io-ts';

const User = t.type({ name: t.string });
const result = User.decode(JSON.parse('{"name":"Ada"}'));

if (result._tag === 'Right') console.log(result.right.name);

// io-ts 的 decode 返回 Either，不会抛异常
console.log('io-ts 在运行时校验结构');

# 编译期 vs 运行期的双保险

type User = { name: string };

function isUser(value: unknown): value is User {
  return typeof value === 'object' && value !== null
    && typeof (value as User).name === 'string';
}

const data: unknown = JSON.parse('{"name":"Ada"}');
if (isUser(data)) console.log(data.name);

function isUser(value) {
  return typeof value === 'object' && value !== null && typeof value.name === 'string';
}

const data = JSON.parse('{"name":"Ada"}');
if (isUser(data)) console.log(data.name);

# 10. 对比总结表

概念 编译期 运行期 危险程度
TypeScript 类型 ✅ 类型检查 ❌ 不存在 🔴 高
as 断言 ✅ 类型覆盖 ❌ 无检查 🔴 高
declare ✅ 类型声明 ❌ 无代码 🟡 中
strictNullChecks ✅ 报错 ❌ 无保障 🟡 中
Enum ✅ 类型检查 ✅ 普通对象 🟡 中
Const Enum ✅ 内联 ❌ 无对象 🟢 低
Interface ✅ 类型检查 ❌ 不存在 🔴 高
类型守卫 ✅ 类型收窄 ✅ 真实检查 🟢 低
运行时验证库 ❌ 无 ✅ 真实验证 🟢 低

# 总结

  1. 类型擦除是核心：TypeScript 的类型在编译后完全消失，运行时没有任何类型信息
  2. 编译选项仅影响编译：即使开启了所有 strict 选项，运行时依然可能出错
  3. as 是危险操作：只应在你绝对确定类型正确时使用
  4. 类型守卫是桥梁：将编译期类型收窄转化为运行时真实检查
  5. 运行时验证是必要补充：对于来自网络、用户输入的数据，必须使用运行时验证库

最佳实践

  • 不要用 as 假装类型安全
  • 使用类型守卫处理复杂的类型收窄
  • 对外部数据使用 zod/io-ts 等运行时验证库
  • 理解 TypeScript 的限制，不要过度依赖编译期检查
