🔍 TypeScript 静态类型与运行时行为差异 - 交互演示

核心问题：编译通过 ≠ 运行时安全

TypeScript 的类型检查仅在编译期生效。 一旦编译完成，所有类型信息都被擦除，生成的 JavaScript 代码中不包含任何类型保障。
// TypeScript 代码 - 编译前 function greet(name: string) { return "Hello, " + name.toUpperCase(); } greet(null); // ❌ 编译报错：Argument of type 'null' is not assignable
// JavaScript 代码 - 编译后（类型擦除） function greet(name) { return "Hello, " + name.toUpperCase(); // 运行时可能崩溃！ } greet(null); // 运行时错误：Cannot read property 'toUpperCase' of null

快速演示

什么是类型擦除？

TypeScript 编译器在编译时会移除所有类型注解，生成的 JavaScript 代码中不包含任何类型信息。

类型注解消失

// TypeScript const name: string = "TypeScript"; const version: number = 4.9; const isAwesome: boolean = true;
// 编译后 (JavaScript) const name = "TypeScript"; const version = 4.9; const isAwesome = true; // 所有类型注解都消失了！

泛型被完全移除

// TypeScript - 泛型函数 function identity<T>(arg: T): T { return arg; }
// 编译后 - T 完全消失 function identity(arg) { return arg; }

typeof T 在运行时永远不对

// TypeScript - 尝试在运行时检查泛型类型 function checkType<T>(arg: T) { console.log(typeof T); // ❌ 永远是 undefined 或具体原始类型 console.log(typeof arg); // ✅ 这是真实的运行时检查 }

strictNullChecks

编译期有效，运行时无任何保障。
即使开启 strictNullChecks，null 和 undefined 在运行时依然是真实存在的值。
// tsconfig.json { "strictNullChecks": true }
// TypeScript - 编译报错 let name: string = null; // ❌ Type 'null' is not assignable to type 'string'
// 但运行时 JavaScript 根本没有类型！ let name = null; console.log(name.toUpperCase()); // 💥 运行时错误！

noImplicitAny

noImplicitAny 让 TypeScript 对隐式 any 类型报错，但这只是编译期检查，运行时 any 依然是 JavaScript 的动态类型。

对比表

编译选项编译期行为运行时保障

noImplicitAny报错隐式 any无任何保障

declare 字段仅用于类型检查

declare 字段在编译后完全消失！ 运行时会报错 "Cannot read property"，因为属性根本不存在。
// TypeScript class MyClass { declare value: string; // 仅类型声明，无运行时代码 } const obj = new MyClass(); console.log(obj.value); // ❌ 编译通过，但运行时报错！

useDefineForClassFields 影响 emit 方式

选项编译行为运行时效果
true使用 Object.defineProperty符合 class 标准语义
false直接赋值可能与预期不符

抽象类字段

抽象字段在编译期强制子类实现，但运行时就只是普通的类继承，没有特殊处理。

Numeric Enum 编译为双向映射对象

// TypeScript enum Status { Pending, Active, Done }
// 编译后 - 双向映射对象 var Status; (function (Status) { Status[Status["Pending" = 0]] = "Pending"; Status[Status["Active" = 1]] = "Active"; Status[Status["Done" = 2]] = "Done"; })(Status || (Status = {}));

Enum 可在运行时被修改（危险！）

Enum 在运行时应被视为常量，但技术上可以修改！修改后会影响所有引用。

Const Enum 完全内联

Const enum 在编译时内联化，不生成任何运行时对象。但使用 --preserveConstEnums 可以保留。

as 只在编译期有效！

类型断言（as）是危险操作。 它只在编译期覆盖类型，运行时完全没有类型检查！
// 危险！编译通过，运行时崩溃 const value = null as string; console.log(value.toUpperCase()); // 💥 TypeError: Cannot read property 'toUpperCase' of null

正确的做法：类型守卫

类型守卫（如 typeof）在运行时是真实检查，可以安全地收窄类型。
// 安全！typeof 在运行时有真实效果 function greet(name: string | null) { if (typeof name === 'string') { return "Hello, " + name.toUpperCase(); } return "Hello, stranger"; }

declare 语句只生成类型

declare 语句仅用于类型检查，编译后完全消失，不生成任何 JavaScript 代码。
// TypeScript declare const GLOBAL_APP: string; console.log(GLOBAL_APP); // 编译报错：GLOBAL_APP 在声明前引用

declare global 只影响类型

declare global 扩展全局类型作用域，但不会在运行时创建任何全局变量！

三斜线指令

/// <reference types="node" /> // 仅用于编译时的类型包含 // 运行时无任何作用

条件类型在编译期求值折叠

条件类型 T extends U ? X : Y 在编译后被"折叠"为具体结果类型，运行时不存在条件类型。
// TypeScript type IsString<T> = T extends string ? "yes" : "no"; type A = IsString<string>; // "yes" type B = IsString<number>; // "no"
// 编译后 - 条件类型消失，只剩具体类型 // A = "yes" (具体字符串字面量) // B = "no" (具体字符串字面量)

never 类型在条件类型中

type ExtractReturn<T> = T extends (...args: any[]) infer R ? R : never; type A = ExtractReturn<typeof console.log>; // void type B = ExtractReturn<string>; // never

误区一：编译通过 = 运行时正确

这是最危险的误区！TypeScript 编译成功只说明类型检查通过，不意味着运行时不会出错。
// 编译通过，但运行时报错 const user = { name: "Alice", age: 25 }; function getEmail(u: { name: string; age: number }) { return u.email.toLowerCase(); // 编译通过！运行时报错 }

误区二：用 as 假装有类型安全

as 只在编译期有效。运行时 null 还是 null，undefined 还是 undefined。
// 危险代码 const data = await fetch(url); const json = await data.json() as { id: number; name: string }; // 如果 JSON 实际是 { error: "Not Found" }，运行时没有保障！

误区三：忽略 undefined/null 的运行时存在

strictNullChecks 只在编译期检查 undefined/null。运行时必须自己处理这些值。

误区四：认为接口会在运行时存在

接口只是类型约束，在编译后完全消失。运行时的 JavaScript 对象没有任何类型信息。

为什么需要运行时验证？

TypeScript 的类型检查只在编译期有效。对于来自网络、用户输入、文件等外部数据，必须在运行时进行验证。

Zod - 运行时验证方案

// Zod 示例 import { z } from 'zod'; const UserSchema = z.object({ id: z.number(), name: z.string(), email: z.string().email() }); // 编译期类型 + 运行时验证 type User = z.infer<typeof UserSchema>; // 验证数据 const result = UserSchema.safeParse(apiResponse); if (result.success) { console.log(result.data); // 类型安全的 User 对象 } else { console.error(result.error); // 验证失败详情 }

实践建议

  • 对外部数据（API、用户输入、文件）使用运行时验证
  • 使用 Zod/io-ts 等库获得编译期 + 运行期的双保险
  • 不要过度依赖 as 断言
  • 使用类型守卫处理复杂的类型收窄
