TypeScript 模块引入机制详解

交互式学习 · 涵盖 import/export、模块解析、paths 配置与常见问题

概念总览

TypeScript 的模块系统建立在 ES6 模块规范之上，并进行了类型层面的扩展。理解模块引入机制是掌握 TypeScript 的基石。

什么是模块？

每个 .ts/.tsx 文件都是一个独立作用域。通过 export 导出，import 导入，实现代码复用和封装。

模块解析

编译器根据导入路径（相对/非相对）和解析策略（Classic/Node），找到实际文件位置的过程。

tsconfig 配置

baseUrl、paths、moduleResolution 等选项控制解析行为，帮助设置路径别名和查找规则。

常见陷阱

导入省略、ESM/CJS 混用、循环引用、.d.ts 查找失败等问题，都有对应的解决方案。

导入类型划分

关联导入 Relative Import

以 /、./、../ 开头的导入，指向本地文件。

import { foo } from './foo'; import foo from '../utils/foo';
非关联导入 Non-relative Import

以模块名直接导入，引用第三方包或内部模块（需配置 baseUrl/paths）。

import $ from 'jquery'; import { Component } from '@angular/core'; import { helper } from '@/utils/helper';

模块解析流程总览

import 语句 -> 解析路径类型 -> 应用解析策略
(Classic / Node) -> 查找文件
(.ts .tsx .d.ts) -> 类型检查 ✓

import 语法全解

TypeScript 支持多种 import 语法，适用于不同场景。理解它们的差异有助于写出更精确的代码。

1. 默认导入

常用 导入模块的 default 导出
foo.ts (导出方)
export default class Foo { } export default function helper() { }
使用
import Foo from './foo'; import helper from './foo';

一个模块只能有一个 default 导出。导入时可以自定义名称。

2. 命名导入

常用 导入指定的命名导出
utils.ts
export const add = (a: number, b: number) => a + b; export const multiply = (a: number, b: number) => a * b; export const VERSION = '1.0.0';
使用
import { add, multiply } from './utils'; import { add as sum } from './utils'; // 重命名 console.log(add(1, 2)); // 3

3. 命名空间导入

进阶 将模块所有导出作为对象的属性访问
import * as Utils from './utils'; console.log(Utils.add(1, 2)); console.log(Utils.multiply(3, 4));

所有命名导出和 default 导出都被放到 Utils 对象下。

4. 类型导入（type-only import）

TS 3.8+ 仅导入类型，编译后完全消除
foo.ts
export type ID = string | number; export interface User { name: string; age: number; } export class Config { }
使用 — 仅类型导入
import type { ID, User } from './foo'; function process(id: ID): User { ... }

编译为 JavaScript 后完全消失，避免运行时依赖，同时解决导入省略问题。

5. 动态导入

异步 返回 Promise，实现代码分割
使用
const module = await import('./heavy-module'); module.doSomething();
回调风格
import('./heavy-module').then(module => { module.doSomething(); });

常用于按需加载大型模块（如路由懒加载），编译产物会分成独立的 chunk。

6. 重导出（re-export）

命名重导出
export { foo, bar } from './module'; export { foo as renamed } from './module';
转发命名导出
整体重导出
export * from './module'; export * as utils from './module';
转发所有导出 / 整体作为命名空间

7. 副作用导入

import './polyfills'; // 执行 polyfills.ts 中的顶级代码，但不导入任何具体绑定

仅执行模块的顶级代码（如注册全局变量、扩展原型），不引入任何绑定。常用于 polyfill 或全局初始化。

模块解析策略

当 TypeScript 遇到 import x from "path" 时，它需要找到对应的文件。这个过程由 模块解析策略 控制。

moduleResolution 配置
classic
"moduleResolution": "classic"
旧版策略，默认用于 es2015/esnext/amd/system 模块
node
"moduleResolution": "node"
Node.js 风格，与 commonjs 模块配合使用

Classic 策略

旧版 了解即可

关联导入（相对路径）：查找 ./path.ts → ./path.d.ts

非关联导入（模块名）：从当前目录向上逐级查找 path.ts → path.d.ts

Node 解析策略

推荐 与 Node.js 模块加载机制一致

相对路径（ ./xxx 或 ../xxx）

  1. 查找 ./xxx.ts, ./xxx.tsx, ./xxx.d.ts
  2. 查找 ./xxx/package.json 的 types 字段
  3. 查找 ./xxx/index.ts, ./xxx/index.tsx, ./xxx/index.d.ts

绝对路径 / 模块名（非相对）

  1. 在 node_modules/ 逐级向上查找 模块名.ts 系列
  2. 查找 node_modules/xxx/package.json 的 types 字段
  3. 查找 node_modules/xxx/index.ts 系列
  4. 查找 node_modules/@types/xxx.d.ts

paths vs aliases

重要区别
特性paths (TS)aliases (打包工具)
作用阶段类型检查 + 编译打包时（Webpack/Vite等）
运行时需要额外配置开箱即用
适用工具tsc, ts-serverWebpack, Vite, Rollup

最佳实践：同时配置 tsconfig paths + 打包工具 alias，保证类型检查和运行行为一致。

tsconfig.json 配置演示

以下是典型项目中模块相关配置的完整示例，逐项说明作用。

完整 tsconfig 示例

{ "compilerOptions": { "module": "commonjs", "moduleResolution": "node", "baseUrl": ".", "paths": { "@/*": ["src/*"], "@components/*": ["src/components/*"] }, "rootDir": "src", "outDir": "dist", "esModuleInterop": true, "allowSyntheticDefaultImports": true } }

baseUrl — 基础路径

所有非相对导入的解析会参考此路径。通常设为 "."（项目根目录）或 "src"。

"baseUrl": "."

paths — 路径别名映射

定义模块名到实际路径的映射。路径相对于 baseUrl。

"paths": { "@/*": ["src/*"], "@components/*": ["src/components/*"], "jquery": ["node_modules/jquery/dist/jquery.min"] }

使用：import Button from '@/components/Button'

module — 输出模块格式

commonjs
"module": "commonjs"
require/exports，兼容性好
esnext
"module": "esnext"
import/export，需打包
nodenext
"module": "nodenext"
Node 官方 ESM 支持
preserve
"module": "preserve"
保留 ESM，不转换

esModuleInterop — ESM/CJS 互操作

启用后 import React from 'react' 能正确导入 CJS 模块。

typeRoots 与 types

"typeRoots": ["./node_modules/@types"], "types": ["node", "express"]

typeRoots：指定查找 @types 的目录范围。
types：明确列出要包含的类型包。

常见问题与解决方案

Cannot find module 'xxx'▼

原因：TypeScript 找不到指定路径的文件。

排查步骤：

  1. 确认文件路径拼写正确（大小写敏感）
  2. 确认文件扩展名（.ts/.tsx/.d.ts）存在
  3. 对于非相对导入，检查 baseUrl 和 paths 配置
  4. 确认 moduleResolution 设置为 node
  5. 对于 npm 包，确认已安装且 @types 存在
.d.ts 类型声明文件找不到▼

排查顺序：

  1. 检查 npm 包是否自带 types 字段（package.json）
  2. 检查 @types/xxx 是否安装
  3. 确认 typeRoots 配置是否覆盖了默认路径
  4. 使用 declare module "xxx" 声明快捷模块
// 快捷声明 — 适用于无类型的第三方模块 declare module "my-untyped-lib" { const value: any; export default value; }
ESM vs CJS 混用问题▼

问题：ES 模块和 CommonJS 模块相互导入时报错。

解决方案：

  1. 启用 esModuleInterop: true
  2. 启用 allowSyntheticDefaultImports: true
  3. 避免在 ESM 项目中混用 require
  4. 使用 import type 明确类型导入
循环引用（Circular Dependency）▼

问题：A 导入 B，B 导入 A，导致 undefined。

解决方案：

  1. 重构设计：将共同依赖抽取到独立模块（C 模块）
  2. 延迟导入：使用动态 import 在函数内部导入
  3. 接口拆分：将类型定义和实现分离
  4. 避免模块级（顶层）的变量相互依赖
// 动态 import 打破循环 async function loadB() { const { B } = await import('./B'); return new B(); }
导入省略（Import Elision）▼

问题：TypeScript 认为 import 只引入类型，在编译后删除该导入，导致模块未执行。

// a.ts — 有副作用的导出 export class Foo { } console.log('a module loaded'); // b.ts — 只导入类型，但编译后 import 被删除 import { Foo } from './a'; // 编译后消失！ // a.ts 的 console.log 不会执行

解决方案：使用 import type 明确声明仅导入类型，或单独导入一次做初始化：

import type { Foo } from './a'; // 明确是类型导入 import './a'; // 单独导入执行副作用
